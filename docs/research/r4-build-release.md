### 2.2 Recommendation: pnpm workspaces with Turborepo

- **pnpm** is the strictest and safest package manager for publishing libraries. Its isolated layout surfaces missing `dependencies` and `peerDependencies` in our own repo instead of in consumers' apps. Catalogs give one React, TypeScript and tsdown version across the repo. Pack and publish rewrite `workspace:` and `catalog:`, and Changesets v3 calls `pnpm pack` and `pnpm publish` directly (verified in [`getPublishTool.ts`](https://github.com/changesets/changesets/blob/main/packages/cli/src/commands/publish/getPublishTool.ts) and [`lib/pnpm.ts`](https://github.com/changesets/changesets/blob/main/packages/cli/src/lib/pnpm.ts)).
- **pnpm 12 or 11.** pnpm 12.11.2 is now the npm `latest` tag. Its maintainers say "v12 should behave the same as v11", with a short list of breaking changes ([12.0 blog](https://pnpm.io/blog/releases/12.0)). The rewrite is new and patch cadence is high (12.10 to 12.13 within a week). Pin the exact version in `devEngines.packageManager`, keep 11.28.x as a fallback, and let Renovate move it after `minimumReleaseAge`. Note that **pnpm 12 fails on unknown `pnpm-workspace.yaml` keys** when the version is pinned, so the skeleton below only uses documented keys.
- **Turborepo** stays because it adds almost no concepts: tasks, `dependsOn`, `outputs`, `inputs`, a cache. Removing it later means replacing `turbo run x` with `pnpm -r x`, which fits the "plug in or out" goal. Turbo 2.11 reads `devEngines.packageManager` and plans to drop support for the top-level `packageManager` field in a future major ([2.11 blog](https://turborepo.dev/blog/2-11)). Avoid the flags deprecated in 2.9 (`--parallel`, `--no-cache`, `--remote-only`, daemon config; see [2.9 blog](https://turborepo.dev/blog/2-9)).
- **Watch `pnpm pipeline`.** It is pnpm's own task runner (since 12.4) and speaks the Turborepo remote-cache API. Once it leaves experimental, it could replace Turborepo with one less dependency. Migrating is mostly a matter of moving the `tasks` block into `pnpm-workspace.yaml`.

**Rejected:**
- **Nx 23.** Strong for large polyglot organisations. For around 5 publishable packages and a few apps it is too much: plugin inference, project graph configuration, and an `nx release` that overlaps with Changesets. Nx Cloud is the paid path, and adoption pulls a lot of Nx-specific configuration.
- **moon 2.x.** Good engineering with WASM toolchains. It still adds a second configuration language and its own toolchain management, the v2 major landed in February 2026, and the JS-library community is smaller.
- **Bun workspaces.** `bun publish` cannot do OIDC trusted publishing or provenance. You would have to pack with Bun and publish with npm. CI would also run on a different runtime than consumers' Node SSR.

### 3.2 Experiment (tsdown 0.23.1, Rolldown 1.2.13, TS 7.0.2, Node 24.16.0)

Setup: a scratch package with `src/button/button.tsx` (`'use client'`, `useState`), `src/card/card.tsx` (server-safe), a barrel `src/index.ts`, `src/internal/**`, `src/unstable/glass-panel`, and `isolatedDeclarations: true`. Findings:

1. **`unbundle: true` produces one output file per source module** (`dist/button/button.js`, `dist/card/card.js`, `dist/utils/cx.js`). `"use client";` **stays on the first line of `button.js` only**. The barrel `dist/index.js` has no directive, so server-safe exports such as `Card` remain Server Components.
2. Rolldown still prints a `MODULE_LEVEL_DIRECTIVE` warning even though the directive is preserved. `inputOptions: { checks: { moduleLevelDirective: false } }` silences it (verified). Pair that with the post-build guard in §5.2.
3. **The oxc d.ts path works with TS 7 installed.** It emits `dist/button/button.d.ts` and so on, with `.js` specifiers (`import { Button } from "./button.js"`).
4. `exports: true` generated `{ ".": "./dist/index.js", "./button": "./dist/button/index.js", "./card": …, "./unstable/glass-panel": …, "./package.json": … }` from the glob entries `['src/index.ts','src/*/index.ts','src/unstable/*/index.ts','!src/internal/**']`. Internal modules were not exported.
5. **publint and attw (`profile: 'esm-only'`) both passed** with plain string exports. No `types` condition is needed because each `.d.ts` sits next to its `.js`.
6. **A CommonJS consumer can `require('@nizivo/ui-exp')` and `require('@nizivo/ui-exp/button')`**, and `react-dom/server.renderToString` renders `<div class="nz-card"><button class="nz-button">…`. This works through `require(esm)` with no `require` condition and no CJS build.
7. **CSS pitfalls found:**
   - (a) A co-located `button.css` imported from `button.tsx` caused Rolldown to emit the JS as **`button2.js`**. The generated `index.d.ts` still referenced `./button.js`, which is a silent mismatch.
   - (b) attw reports `No resolution` for CSS subpaths such as `./styles.css`. The fix is `attw.excludeEntrypoints: [/\.css$/]` (verified).
   - (c) Shipping CSS through `copy: [{ from: 'styles/*.css', to: 'dist/css' }]` plus `exports.customExports` (`./css/*`, `./styles.css`) passes publint and attw (verified). Note that `copy` with a directory `from` nests the folder; use a glob.

### 3.3 Recommendation: tsdown in unbundle mode, behind a shared preset

- tsdown is the only option that does everything a design-system package needs in one place: per-module ESM, directive preservation, fast d.ts generation, generated `exports`, and built-in publint and attw. The tsdown docs also say "CJS is in maintenance-only mode" and encourage new libraries to be ESM-only ([output format](https://tsdown.dev/options/output-format)).
- **Pin the exact version** (0.x minors are breaking; 0.23 removed and renamed options). Keep all options in `tooling/tsdown-config`. Because output is transpile-only and unbundled, switching to `tsc` or obuild later changes nothing for consumers.
- **Always set `platform: 'neutral'` and `target: 'es2022'` explicitly.** tsdown's defaults are `platform: 'node'`, which forces `.mjs` through `fixedExtension`, and a `target` that falls back to `engines.node`. With those defaults, adding `engines` later would silently change the emitted syntax ([UserConfig reference](https://tsdown.dev/reference/api/Interface.UserConfig)).
- Set **`hash: false`** so paths are deterministic. Leave `minify` at its default `'dce-only'`: output stays readable and consumers minify. No JS sourcemaps are needed for readable output.

**Rejected:**
- **tsup.** Unmaintained, and its npm page itself points to tsdown.
- **Vite library mode.** It is app-centric. It needs an extra d.ts plugin, a hand-written `exports` map and manual `preserveModules`. Keep Vite for the playgrounds and Storybook.
- **unbuild.** Frozen.
- **obuild.** Pre-stable.
- **bunchee 7.** Reasonable and good with directives, but it follows a single maintainer and inverts the workflow (`exports` drives the build). It is the fallback if tsdown stalls.
- **plain `tsc`.** It is the emergency fallback. It has no CSS handling, no `exports` generation and no lint integration.

## 4. ESM-only or dual CJS/ESM in 2026: ESM-only

Evidence:
- Every supported Node line (22.12+, 24, 26) runs `require(esm)` unflagged, and it has been non-experimental since 25.4 ([Node docs](https://nodejs.org/docs/latest-v26.x/api/modules.html#loading-ecmascript-modules-using-require)). I verified this locally on 24.16 (§3.2 item 6).
- All target frameworks are ESM-native: Next.js 16 App Router, plus Vite 8 behind Vite SPA, React Router v7 framework mode, Astro and TanStack Start.
- A dual build doubles output, risks the dual-package hazard (two React context instances when one consumer path uses `require` and another uses `import`), and complicates `"use client"`.

**Jest.** Jest 30.5 can `require()` an ESM-only package **only on Node ≥ 24.9**, resolving through the `require`, `module-sync` or `default` conditions. A package that exposes ESM only under `import` fails with `ERR_PACKAGE_PATH_NOT_EXPORTED` ([Jest ESM docs](https://jestjs.io/docs/ecmascript-modules)). That is why our `exports` use the string (default) form and never an `import`-only object. On Node 22, Jest users need `transformIgnorePatterns: ['node_modules/(?!@nizivo)']` plus a transform. Whether Jest still needs `--experimental-vm-modules` in this path is **UNVERIFIED**. The docs recommend Vitest 5.

Rules for exports:
- Use `"./x": "./dist/x/index.js"` (string = default), or `{ "types": …, "default": … }` if a `types` condition is ever needed. `types` goes first and `default` last ([Node packages docs](https://nodejs.org/api/packages.html)).
- **No top-level await anywhere** in the package graph, because it breaks `require(esm)` with `ERR_REQUIRE_ASYNC_MODULE`. Enforce this with a lint rule.
- Set `"type": "module"` and emit `.js` files.

## 5. Output shape, `"use client"` and declarations

### 5.1 Per-module output (`unbundle`)
Unbundled output lets each consumer bundler tree-shake at file granularity. It keeps directives per module, matches source paths in stack traces, and makes subpath exports trivial. The barrel is a list of re-exports, so with `"sideEffects": ["**/*.css"]` bundlers can drop unused modules.

### 5.2 `"use client"` policy
- Put `'use client'` **only at the top of leaf modules that use state, effects, refs, event handlers or browser APIs**. Never put it in barrels (`index.ts`) or in purely presentational modules. The [publira PR](https://github.com/publira/publira/pull/2938) shows the cost of blanket directives: about 20 modules needlessly became client references.
- Context providers and hooks modules are client modules. Server-safe modules must not import them.
- Add a **post-build guard** that fails if a source module starting with `"use client"` lost it in `dist`. The script below was tested: it passes on a correct build and fails after the directive is stripped.

```js
// tooling/scripts/check-client-directives.mjs — usage: node check-client-directives.mjs packages/ui
import { readFile, glob } from 'node:fs/promises'
import path from 'node:path'
const pkgDir = path.resolve(process.argv[2] ?? '.')
const DIRECTIVE = /^\s*(?:\/\/[^\n]*\n|\/\*[\s\S]*?\*\/\s*)*['"]use client['"]/
const failures = []; let checked = 0
for await (const rel of glob('src/**/*.{ts,tsx}', { cwd: pkgDir })) {
  if (rel.endsWith('.d.ts') || /\.(test|stories)\.tsx?$/.test(rel)) continue
  if (!DIRECTIVE.test(await readFile(path.join(pkgDir, rel), 'utf8'))) continue
  checked++
  const out = path.join(pkgDir, 'dist', rel.replace(/^src[\\/]/, '').replace(/\.tsx?$/, '.js'))
  const built = await readFile(out, 'utf8').catch(() => null)
  if (built === null) failures.push(`${rel}: expected ${path.relative(pkgDir, out)}`)
  else if (!DIRECTIVE.test(built)) failures.push(`${rel}: "use client" missing in ${path.relative(pkgDir, out)}`)
}
if (failures.length) { console.error(failures.join('\n')); process.exit(1) }
console.log(`use-client check: ${checked} client module(s) OK`)
```

### 5.3 Declarations and TypeScript 7
- Set **`isolatedDeclarations: true`**. rolldown-plugin-dts then picks the **oxc** generator automatically ("`oxc` if `compilerOptions.isolatedDeclarations` is enabled" — [repo](https://github.com/sxzz/rolldown-plugin-dts)). It is the fastest path, needs no TypeScript API, and forces explicit return types on exported functions, which is useful discipline for a public design-system API (`export function Button(p: ButtonProps): JSX.Element`).
- **TS 7.0 has no stable programmatic API** (expected in 7.1; the timing is **UNVERIFIED**). Status of tools that depend on that API:
  - typescript-eslint: **confirmed incompatible** (supported range `<6.1`; [#12518](https://github.com/typescript-eslint/typescript-eslint/issues/12518)).
  - Storybook `react-docgen-typescript`, api-extractor, typedoc and ts-morph: incompatibility is **inferred, not tested**.
  - Storybook's default `reactDocgen: 'react-docgen'` does its own analysis without the TS compiler ([Storybook docs](https://storybook.js.org/docs/configure/integration/typescript.md)), so it is fine.
- **Position:**
  - Use TS 7.0.x at the root for `tsc --noEmit` (fast typecheck) and as the base for oxlint type-aware linting, which **requires** TS ≥ 7.
  - Generate d.ts with oxc.
  - If a tool that needs the TS API becomes necessary before 7.1, put it in its own private workspace package with a local `typescript@^6` devDependency. pnpm's per-package resolution keeps that isolated.
  - Alternatively stay on TS 6 at the root until 7.1. Weigh that against losing oxlint type-aware linting.

## 6. Package layout and `exports`

### 6.1 Packages

Keep the number of published packages small. Each npm package needs its own trusted-publisher entry, created interactively with 2FA. Namespace-wide `@scope/*` OIDC configuration is still only a roadmap item ([npm announcement](https://github.com/orgs/community/discussions/201329)).

The Starter and Pro plans therefore **cannot fetch variables in CI**. The token build must read a **committed JSON export** (from a plugin or Figma MCP `get_variable_defs`). This is handed off to the tokens topic.

### 6.2 `exports` map design (`@nizivo/ui`)
- **Per-component subpaths are the primary contract**: `@nizivo/ui/button`, `@nizivo/ui/select`, and so on. Each component folder is `src/<name>/index.ts`.
- **The root barrel `@nizivo/ui` is for convenience.** It is a thin list of `export *` re-exports with no code and no directive.
  - Dev servers do not tree-shake, so barrels cost dev compile time ([analysis](https://reactuse.com/blog/barrel-files-tree-shaking/)). Subpaths avoid that.
  - Next's `optimizePackageImports` is still "experimental … not recommended for production" ([Next docs](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports)), so do not rely on it.
- **`./unstable/*`** holds work-in-progress components. They are documented as **not covered by semver**, and the lane lets components be plugged in and out freely. Promoting one means moving `src/unstable/x` to `src/x` and keeping a deprecated re-export for one minor release.
- **CSS subpaths:** `./styles.css` (everything) and `./css/*` (per component).
- `./package.json` is exported for tooling.
- `src/internal/**` is **never** exported (it is excluded from entries; verified).
- The map is **generated** by tsdown (`exports: true` plus `customExports` for CSS), **committed**, and guarded in CI with `git diff --exit-code -- 'packages/*/package.json'` after the build. The published manifest then always matches the repo.

### 6.3 CSS build contract (handed to the styling report)
1. **No `import './x.css'` in any JS module.** These imports break Node SSR externalisation (Vite externalises dependencies in SSR — [Vite SSR](https://vite.dev/guide/ssr)), Jest and plain Node. They also triggered the `button2.js` collision in §3.2.
2. CSS is emitted to `dist/css/**`, either by `copy` or by a separate Lightning CSS step, and exposed as `./styles.css` and `./css/*`.
3. CSS basenames must never collide with TS module basenames in the same folder, in case the styling engine needs co-location later.
4. Components depend only on **CSS custom properties** (`--nz-*`) and stable class names (`nz-*`). Prefixes are configurable at token build time.
5. Set `"sideEffects": ["**/*.css"]`. Rolldown honours `sideEffects` globs, and patterns without `/` match at any depth ([Rolldown docs](https://rolldown.rs/reference/InputOptions.treeshake)).

If the styling report picks a zero-runtime engine that emits CSS from TS (for example vanilla-extract or Pigment-style), that build step must output to `dist/css` and follow rules 1–5.

### 6.4 Manifest fields
- `"type": "module"`.
- `"files": ["dist"]`. pnpm 12.13 has a fix for `files: []`, and 12.11.1 stops including `.npmignore`/`.gitignore` ([releases](https://github.com/pnpm/pnpm/releases)).
- `"sideEffects": ["**/*.css"]`.
- `"engines": { "node": ">=22.12.0" }`. This is the SSR and tooling floor where `require(esm)` is unflagged, and Node 20 is EOL. The CI-side requirement for trusted publishing (Node ≥ 22.14 and npm CLI ≥ 11.5.1, [npm docs](https://docs.npmjs.com/trusted-publishers/)) is separate.
- **peerDependencies**: `react` and `react-dom` with a literal range `^19.0.0`. Do **not** use `catalog:` here, or the narrower catalog range would be published. `@types/react` is an optional peer (`peerDependenciesMeta`), because the published `.d.ts` files import from `react`.
- `"publishConfig": { "access": "public" }`. A scoped package's first publish defaults to restricted.
- `repository: { type, url, directory }`. The URL must **exactly** match the GitHub repo ("All fields are case-sensitive" — [npm docs](https://docs.npmjs.com/trusted-publishers/)).

### 6.5 Plug-in / plug-out seams the build enforces
1. **Packages are swappable units.** The `exports` map is the only contract. Everything under `src/internal` can change freely, and knip flags unused exports.
2. **The `unstable/` lane** holds work-in-progress components outside semver.
3. **Tokens connect to components only through CSS variables.** A different token source or a customer theme is just a different CSS file.
4. **Behaviour primitives are wrapped** in `src/internal/primitives/*` adapters. A lint rule (`no-restricted-imports`, which oxlint implements) forbids importing the third-party primitive library anywhere else. Third-party types never appear in public `.d.ts`; this is reviewed through the API snapshot below.
5. **Heavy modules** go in separate packages (`charts`, `lab`) with optional peers and `import()` for 3D or shader code.
6. **Tooling is swappable.** Unbundled output means tsdown can be replaced by tsc or obuild. Plain scripts mean Turborepo can be replaced by `pnpm -r`. Changesets entries are plain markdown.
7. **API snapshot.** CI concatenates `dist/**/*.d.ts` into a committed `api/<pkg>.d.ts`. A PR that changes that file must include a changeset. This is a lightweight stand-in for api-extractor while TS 7 has no API.

## 9. Publishing to npm

### 9.1 Current status (October 2026)
- **Trusted publishing (OIDC)**:
  - Supported for GitHub Actions on **GitHub-hosted runners only**, GitLab.com and CircleCI. Self-hosted runners are not supported.
  - Requires npm CLI ≥ 11.5.1 and Node ≥ 22.14. OIDC for dist-tags requires npm ≥ 11.21.0 or 12.2.0.
  - Up to 10 configurations per package. Existing ones cannot be edited, only deleted and recreated.
  - **Provenance is generated automatically** for public repo plus public package.
  - The package-settings option "**Require two-factor authentication and disallow tokens**" does not affect OIDC.
  - Source: [npm docs](https://docs.npmjs.com/trusted-publishers/), last edited 2026-10-06.
- **Configs created after 2026-09-03 default to `npm stage publish` only.** You must explicitly allow `npm publish`, and `npm dist-tag` if used ([npm docs](https://docs.npmjs.com/trusted-publishers/)).
- **Since 2026-10-02, unvalidated configs expire after 48 hours.** A config is validated by its first successful publish. Changing the repository identity starts a fresh window. npm also **rejects OIDC tokens from `issue_comment`** events, in addition to `pull_request_target` ([GitHub changelog](https://github.blog/changelog/2026-10-02-unvalidated-npm-trusted-publishing-configurations-now-expire/)). Background: the "repo-name reclaim" flaw affecting over 1,500 packages ([The Hacker News](https://thehackernews.com/2026/10/github-tightens-npm-publishing-after.html)).
- **Staged publishing**: `npm stage publish` (npm ≥ 11.15.0) puts a version in a queue, and a maintainer approves it with 2FA (`npm stage approve <id>` or the web UI). Staging a **new** package publishes a public `0.0.0-stage` placeholder ([docs](https://docs.npmjs.com/staged-publishing), [changelog](https://github.blog/changelog/2026-10-02-npm-staged-publishing-now-supports-creating-new-packages/)). pnpm 12 adds `pnpm stage approve` for batches ([12.0 blog](https://pnpm.io/blog/releases/12.0)).

### 9.2 What the npm banner means ("tokens that bypass 2FA are being restricted — account changes (Aug 2026) and direct publishing (Jan 2027)")
- **Phase 1, early August 2026 (in effect):** 2FA-bypass granular tokens can no longer create or delete tokens, change package access or maintainers, **edit trusted-publisher config**, or manage org and team membership. Each of these needs an interactive 2FA challenge ([changelog 2026-07-31](https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/)).
- **Phase 2, targeted January 2027:** bypass tokens **lose direct `npm publish`**. They will only be able to read private packages and *stage* publishes for a human to approve with 2FA ([changelog 2026-07-08](https://github.blog/changelog/2026-07-08-npm-install-time-security-and-gat-bypass2fa-deprecation/), [discussion #201329](https://github.com/orgs/community/discussions/201329)). This is a target date, not a guarantee.
- **Effect on Nizivo:** the change does not affect us if we **never put an npm token in CI**. Publishing goes through OIDC trusted publishing (unaffected), and all npm admin work (creating packages, adding trusted publishers, maintainers) is done interactively by humans with 2FA. Granular tokens also expire after at most 90 days ([Changesets guide](https://changesets.dev/guide/automating)), so a token-based design would need rotation anyway.

### 9.3 Setup checklist, per package (do this once and record it in `RELEASING.md`)
1. Make sure the GitHub repo is **public** (required for provenance) and owned by the Neev Technologies org. Choose the final org and repo slug **before** step 4, because renaming invalidates the binding.
2. Each `package.json` has `"publishConfig": { "access": "public" }` and `"repository": { "type": "git", "url": "git+https://github.com/<org>/<repo>.git", "directory": "packages/<name>" }`. The URL must match exactly and is case-sensitive.
3. **Bootstrap the package name**, because OIDC cannot create new packages yet. Either:
   - (a) a maintainer runs an interactive `npm publish --access public` of `0.0.0` from a clean checkout, with 2FA; or
   - (b) `npm stage publish`, which creates the public `0.0.0-stage` placeholder, then `npm stage approve` with 2FA.
4. npmjs.com → package → Settings → **Trusted Publisher → GitHub Actions**: org `<org>`, repo `<repo>`, workflow filename **`release.yml`**, environment **`npm`**. **Tick "npm publish"** (and "npm dist-tag" if you will move tags). The post-2026-09-03 default is stage-only.
5. **Within 48 hours**, merge a changeset so `release.yml` publishes the first real version through OIDC. This validates the config. If you miss the window, delete and recreate the config.
6. Package Settings → Publishing access → **"Require two-factor authentication and disallow tokens."**
7. Deprecate any `0.0.0` or `0.0.0-stage` placeholder: `npm deprecate @nizivo/x@0.0.0 "placeholder"`.
8. GitHub repo → Settings → Environments → `npm`: restrict deployment branches to `main`. Optionally add **required reviewers**. This gives a human gate equivalent to staged publishing, which Changesets does not support.
9. GitHub repo → Settings → Actions → General: enable "Allow GitHub Actions to create and approve pull requests", or (recommended) use a GitHub App token for the version PR.
10. Create a GitHub App (e.g. "nizivo-release-bot") with contents and pull-requests write access. Store `vars.RELEASE_BOT_CLIENT_ID` and `secrets.RELEASE_BOT_PRIVATE_KEY`. **PRs created with `GITHUB_TOKEN` do not trigger `pull_request` workflows**, so without the App token the Version Packages PR would run no CI.

**Day-1 dry run (open item).** Changesets v3 pack and publish run `pnpm pack --out <tgz>` and `pnpm publish <tgz> --access … --tag … --no-git-checks` (verified in source). The publish job therefore needs a pnpm that exchanges GitHub OIDC tokens. pnpm 11+ does this natively. pnpm 12.11.0 fixed `--provenance=false` handling, and 12.12.1 (on `next-12`) fixed `NPM_ID_TOKEN` audience matching, which matters mainly for GitLab and CircleCI. **I did not verify** that `pnpm@12.11.2` + `pnpm publish <tarball>` + GitHub OIDC works end to end. Test it on a throwaway scoped package before the first real release, and pin whichever pnpm version passes.

### 9.4 `.github/workflows/release.yml` (pnpm adaptation of the official Changesets trusted-publishing split)

Pin every action to a full commit SHA (shown here as tags for readability).

```yaml
name: Release
on:
  push:
    branches: [main]
permissions: {}                       # each job opts in
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false

jobs:
  select-mode:
    runs-on: ubuntu-latest
    permissions: { contents: read }
    outputs:
      mode: ${{ steps.select.outputs.mode }}
      publish-plan-artifact-id: ${{ steps.select.outputs.publish-plan-artifact-id }}
    steps:
      - uses: actions/checkout@v7          # pin SHA
        with: { persist-credentials: false }
      - uses: pnpm/setup@v3                # installs pnpm + Node from devEngines, runs pnpm install
        with: { require-lockfile: true }
      - id: select
        uses: changesets/action/select-mode@v2

  version:
    needs: select-mode
    if: needs.select-mode.outputs.mode == 'version'
    runs-on: ubuntu-latest
    permissions: { contents: read }     # writes go through the App token
    steps:
      - id: app-token
        uses: actions/create-github-app-token@v3
        with:
          client-id: ${{ vars.RELEASE_BOT_CLIENT_ID }}
          private-key: ${{ secrets.RELEASE_BOT_PRIVATE_KEY }}
      - uses: actions/checkout@v7
        with: { persist-credentials: false }
      - uses: pnpm/setup@v3
        with: { require-lockfile: true }
      - uses: changesets/action/version@v2
        with:
          github-token: ${{ steps.app-token.outputs.token }}   # so CI runs on the Version PR
          commit-message: 'chore(release): version packages'
          pr-title: 'chore(release): version packages'
        env:
          GITHUB_TOKEN: ${{ steps.app-token.outputs.token }}   # for @changesets/changelog-github

  pack:
    needs: select-mode
    if: needs.select-mode.outputs.mode == 'publish'
    runs-on: ubuntu-latest
    permissions: { contents: read }     # NO id-token here: this job runs build scripts
    outputs:
      pack-dir-artifact-id: ${{ steps.pack.outputs.pack-dir-artifact-id }}
    steps:
      - uses: actions/checkout@v7
        with: { persist-credentials: false }
      - uses: pnpm/setup@v3
        with: { require-lockfile: true }
      - run: pnpm turbo run build check:package --filter='./packages/*' --force   # never trust remote cache for release artifacts
      - id: pack
        uses: changesets/action/pack@v2   # runs `changeset pack` → `pnpm pack` (rewrites workspace:/catalog:)
        with:
          publish-plan-artifact-id: ${{ needs.select-mode.outputs.publish-plan-artifact-id }}

  publish:
    needs: pack
    runs-on: ubuntu-latest              # GitHub-hosted (required for OIDC)
    environment: npm                    # must equal the environment set in npm's trusted-publisher config
    permissions:
      contents: write                   # git tags + GitHub Releases
      id-token: write                   # OIDC → npm; provenance is automatic
    steps:
      - id: app-token                   # tags + Releases are created by the release App, so the tag ruleset (§10) can allow only the App
        uses: actions/create-github-app-token@v3
        with:
          client-id: ${{ vars.RELEASE_BOT_CLIENT_ID }}
          private-key: ${{ secrets.RELEASE_BOT_PRIVATE_KEY }}
      - uses: actions/checkout@v7
        with: { persist-credentials: false }
      - uses: pnpm/setup@v3             # @changesets/cli must be installed; pnpm ≥ 11 does the OIDC exchange
        with: { require-lockfile: true }
      - uses: changesets/action/publish@v2
        with:
          github-token: ${{ steps.app-token.outputs.token }}   # the sub-action always pushes tags via the GitHub API
          pack-dir-artifact-id: ${{ needs.pack.outputs.pack-dir-artifact-id }}
          create-github-releases: true
```

If the App token were left out, the publish sub-action would tag with `github.token` (github-actions[bot]). A tag ruleset limited to the App would then reject the tags *after* npm has already published. The result is the "exited non-zero, but some packages were published" path in [`src/publish/index.ts`](https://github.com/changesets/action/blob/main/src/publish/index.ts). Either keep the App token here, or drop the tag restriction from §10.

The job layout and permissions follow [changesets.dev/guide/automating](https://changesets.dev/guide/automating). The input names come from the sub-action `action.yml` files ([publish](https://github.com/changesets/action/blob/main/publish/action.yml), [pack](https://github.com/changesets/action/blob/main/pack/action.yml), [select-mode](https://github.com/changesets/action/blob/main/select-mode/action.yml), [version](https://github.com/changesets/action/blob/main/version/action.yml)). `client-id` is the current input of create-github-app-token v3; `app-id` is deprecated.

## 10. Repository governance

- **Renovate, not Dependabot.** GitHub's docs list Dependabot pnpm support only for "v7, v8, v9, v10" ([GitHub docs](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories)). Renovate reads `pnpm-workspace.yaml` and catalogs ([Renovate docs](https://docs.renovatebot.com/modules/manager/npm/)). Set the same release-age window in pnpm and Renovate. Otherwise Renovate opens PRs that pnpm refuses to install ([example](https://github.com/supabase/supabase/pull/50417)).
- **GitHub rulesets on `main`:**
  - Require PRs with 1 approval from code owners.
  - Required status checks: `verify`, and `ssr-matrix` in the merge queue.
  - Linear history, a merge queue, and no force pushes or deletions.
  - Restrict creation of `@nizivo/*@*` tags to the release App. This requires the App token in the `publish` job (§9.4), and the App needs `contents: write`.
- **CODEOWNERS:** `/packages/tokens/ @<org>/design-eng`, `/packages/ui/ @<org>/ui-core`, `/.github/ @<org>/maintainers`, `/tooling/ @<org>/maintainers`, `/.changeset/config.json @<org>/maintainers`.
- **Actions hygiene:**
  - Default to `permissions: {}`.
  - SHA-pin all actions (Renovate `helpers:pinGitHubActionDigests`).
  - Use `persist-credentials: false`.
  - Never use `pull_request_target` or `issue_comment` for anything that builds or publishes.
  - `id-token: write` appears only on the `publish` job.
- **Turborepo remote cache:** Vercel (free) with `TURBO_REMOTE_CACHE_SIGNATURE_KEY`, opting into the `longerSignatureKey` future flag (32-byte key — [2.9](https://turborepo.dev/blog/2-9)). Release builds use `--force`.
- Also add **SECURITY.md**, issue and PR templates, a `RELEASING.md` runbook (§9.3), `LICENSE`, `CONTRIBUTING.md`, and optionally `.nvmrc` pointing at Node 24.

export function libraryPreset(overrides: UserConfig = {}): UserConfig {
  return defineConfig({
    entry: ['src/index.ts', 'src/*/index.ts', 'src/unstable/*/index.ts', '!src/internal/**'],
    platform: 'neutral',          // never default 'node' (forces .mjs, node target)

        exp['./styles.css'] = './dist/css/index.css'

## 13. Risks and mitigations

| Risk | Likelihood / impact | Mitigation |
|---|---|---|
| tsdown is 0.x and minors break (0.23 removed options) | Medium / medium | Pin exactly. Single preset. Renovate approval for minors. Unbundled output means fallback to `tsc` emit or bunchee with no consumer change |
| pnpm 12 Rust rewrite is new; publish/OIDC regressions (pnpm 11 had OIDC 404s — [#11513](https://github.com/pnpm/pnpm/issues/11513)) | Medium / high (release blocked) | Pin with devEngines. Day-1 dry run against a throwaway package. Fallback to pnpm 11.28.x |
| TS 7 has no programmatic API: typescript-eslint, docgen-typescript, api-extractor and typedoc unavailable | High / low–medium | oxlint type-aware, Storybook `react-docgen`, d.ts snapshot instead of api-extractor. Isolate TS-6-only tools per package. Revisit at TS 7.1 |
| oxfmt is beta | Low / low | Formatting is reversible. Swap to Biome or Prettier in one file |
| npm trusted publishing keeps changing (48 h expiry, stage-only default, event restrictions) | Medium / medium | Follow the §9.3 runbook. Watch the [GitHub changelog](https://github.blog/changelog/) npm label. Keep few packages |
| No namespace-wide OIDC, so every new package needs interactive 2FA setup | Certain / low | Small package count. Batch setup in a scheduled "package onboarding" session |
| Jan 2027 bypass-token change | Certain / none (no tokens used) | Never add `NPM_TOKEN`. Disallow tokens per package |
| Remote-cache poisoning into release tarballs | Low / high | Signed cache (`TURBO_REMOTE_CACHE_SIGNATURE_KEY` + `longerSignatureKey`), `--force` on the release build, `id-token` only in the publish job (which runs no build) |
| Jest consumers on Node < 24.9 cannot `require()` ESM-only | Medium / low | Document `transformIgnorePatterns` and recommend Vitest. String `exports` keep `require(esm)` working on Node ≥ 22.12 |
| CSS-in-JS imports or basename collisions from the styling decision | Medium / medium | §6.3 contract, attw `excludeEntrypoints`, tarball-based SSR matrix |
| `"use client"` lost or overused | Low / high (RSC break) | Unbundle, the guard script, review checklist, Next playground |
| Changesets v3 is only 2 months old; staged publishing unsupported | Low / medium | Pin 3.0.x. Use a GitHub environment reviewer as the human gate |
| pkg.pr.new (0.0.x, third-party) unavailable | Low / low | Previews are optional. Fall back to snapshot `canary` (needs a second trusted-publisher entry) |
| size-limit-action unmaintained since 2024 | Medium / low | Run `size-limit --json` with a custom comment |

## 14. Rejected alternatives (summary)
- **Nx / moon:** heavier than a library monorepo needs, more lock-in. **Bun workspaces:** no OIDC or provenance in `bun publish`. **pnpm pipeline:** experimental.
- **tsup:** unmaintained. **Vite lib mode:** app-centric, no d.ts or exports generation. **unbuild:** frozen. **obuild:** pre-stable. **bunchee:** single maintainer, kept as fallback. **plain tsc:** kept as emergency fallback.
- **Dual CJS/ESM:** unnecessary given `require(esm)` on every supported Node, and it risks a dual React-context hazard.
- **Single entry only:** dev-time barrel cost, and `optimizePackageImports` is experimental. **Per-component npm packages** (`@nizivo/button`): one trusted-publisher setup per component, which is impractical under current npm OIDC rules.
- **ESLint 10 + typescript-eslint:** cannot run on TS 7. **Biome:** solid fallback, with smaller React and a11y coverage than oxlint's native jsx-a11y port.
- **release-please / semantic-release:** commit-message-driven, which is worse for consumer-facing design-system changelogs; semantic-release is weak in monorepos.
- **Token-based publishing / staged publishing via Changesets:** tokens are being restricted, and Changesets does not support staged publishing.
- **Dependabot:** pnpm 11/12 not supported per its docs.
