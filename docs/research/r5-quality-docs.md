| Criterion | Storybook 10.6 (react-vite) | Ladle 5.1 | Histoire 1.0 beta |
|---|---|---|---|
| Last release | 2026-10-12, very active | 2025-11-04, unreleased commits Jun 2026 | 2026-01-07 beta |
| React support | First-class | React-only | **None published** (Vue, Svelte, Nuxt only) |
| Vite builder | Yes (Vite 5–8) | Yes (Vite-native) | Yes |
| Test integration | **Vitest addon**: stories become browser-mode tests via portable stories, with coverage and sharding ([docs](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)) | None built in | No (Vue) |
| A11y | axe addon integrated with the Vitest addon; `test: 'error'` fails CI ([docs](https://storybook.js.org/docs/writing-tests/accessibility-testing)) | axe addon, UI only | – |
| VRT ecosystem | Chromatic (first-party), Argos Vitest plugin | Bring your own | – |
| Story format | CSF3 / CSF Factories | CSF3 (compatible) | Vue SFC stories |
| Weight / speed | Heavier, but Vite builder and lazy compilation help | Fastest | Fast |
| AI/MCP | `@storybook/addon-mcp` (10.3+) ([10.3 blog](https://storybook.js.org/blog/storybook-10-3/)) | – | Has MCP |
| Swap cost later | – | Low if stories stay CSF3 | n/a |

**Recommendation: Storybook 10.6 (`@storybook/react-vite`), pinned `~10.6`, upgrading to 11 after GA.**
- Use `react-vite`, not `@storybook/nextjs`. SB 11 deprecates `@storybook/nextjs`, and the components must be framework-agnostic anyway, so the workshop should not inject Next.js mocks.
- Keep stories in **plain CSF3 objects**. CSF Factories (`preview.meta()`) give better types but tie stories to a Storybook preview module, and Ladle cannot read them. CSF3 keeps the workshop replaceable.
- Storybook is used as a **workshop and test harness, not the public docs**. `addon-docs` stays installed for internal autodocs but is not the docs product.
- Storybook does not test RSC. RSC coverage comes from the fixture apps (§6).

**Rejected:** Histoire has no React support. Ladle has no Vitest/portable-stories test integration and no releases in 11 months; it is a viable emergency fallback precisely because it reads CSF3.

### 2.1 Architecture: one example, many consumers

```
packages/react/src/button/
  Button.tsx
  Button.module.css | button.css        (styling layer, decided in another track)
  button.examples/                      ← plain React, no Storybook imports
    Variants.example.tsx
    Sizes.example.tsx
  Button.stories.tsx                    ← CSF3: imports examples + adds edge-case stories, args, play()
  Button.test.tsx                       ← Vitest browser: behaviour/keyboard/ARIA
  Button.test-d.ts                      ← expect-type: public prop types
  api/Button.json                       ← generated manifest (props, defaults, data-attrs, CSS vars)
```

The rule: **examples are the contract**. The docs site renders `*.example.tsx` together with its source, highlighted by Shiki. Stories wrap the examples and add edge cases such as long text, RTL, forced colours and loading states. Tests import components directly. Removing Storybook deletes only `*.stories.tsx` and one Vitest project. Replacing the docs framework leaves examples and manifests untouched.

```ts
// .storybook/main.ts
import type { StorybookConfig } from '@storybook/react-vite';

export default {
  framework: '@storybook/react-vite',
  stories: ['../packages/*/src/**/*.stories.@(ts|tsx)'],
  addons: [
    '@storybook/addon-docs',
    '@storybook/addon-a11y',
    '@storybook/addon-vitest',
    '@storybook/addon-themes',
    'storybook-addon-pseudo-states',
  ],
  typescript: { reactDocgen: 'react-docgen' }, // Babel-based; TS-7 safe (see §7)
} satisfies StorybookConfig;
```

```ts
// .storybook/preview.ts
import type { Preview } from '@storybook/react-vite';
import { withThemeByDataAttribute } from '@storybook/addon-themes';
import '@nizivo/tokens/css';          // tokens layer (swappable)
import '@nizivo/react/styles.css';    // styling layer (swappable)

export default {
  decorators: [
    withThemeByDataAttribute({
      themes: { light: 'light', dark: 'dark' },
      defaultTheme: 'light',
      attributeName: 'data-theme',
    }),
  ],
  parameters: {
    a11y: {
      test: 'error', // violations fail Vitest/CI
      options: { runOnly: ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'] },
    },
    // Canonical mode declaration: read by Chromatic AND Argos → VRT vendor is swappable
    // VERIFY for SB10: Storybook 9+ changed the viewport global's shape; Chromatic mode docs may
    // expect `viewport: { value: 'desktop' }` or a pixel width instead of a bare string (UNVERIFIED).
    chromatic: {
      modes: {
        'light desktop': { theme: 'light', viewport: 'desktop' },
        'dark desktop':  { theme: 'dark',  viewport: 'desktop' },
      },
    },
    viewport: {
      options: {
        desktop: { name: 'Desktop', styles: { width: '1440px', height: '900px' } },
        tablet:  { name: 'Tablet',  styles: { width: '834px',  height: '1112px' } },
        mobile:  { name: 'Mobile',  styles: { width: '390px',  height: '844px' } },
      },
    },
  },
} satisfies Preview;
```

The viewport sizes mirror the Figma "Responsive" modes (Desktop, Tablet, Mobile); take the exact widths from the Figma variables. In VRT, force the Motion variables' "Reduced" mode (or `prefers-reduced-motion: reduce`) so spring animations cannot cause flaky diffs.

## 3. Unit and interaction testing: Vitest Browser Mode vs jsdom + Testing Library

| Criterion | Vitest 5 Browser Mode (Playwright provider) | jsdom 30 / happy-dom 21 + Testing Library |
|---|---|---|
| Fidelity | Real Chromium, Firefox and WebKit: layout, `:focus-visible`, pointer events, `inert`, `popover`, `<dialog>`, CSS cascade layers, `getComputedStyle`, `ResizeObserver` | No layout and no real CSS. Popover, anchor positioning and focus behaviour are partially or wrongly emulated |
| Fit with zero-runtime CSS | Tests see the real stylesheet (contrast, `display:none`, forced colours) | Static CSS is effectively invisible |
| Speed | Slower cold start. Vitest 5 cites big Browser Mode gains ([blog](https://vitest.dev/blog/vitest-5.html)) | Fast |
| Debugging | Vitest 5 **Trace View** (`browser.traceView`) and ARIA-tree locator errors | DOM dumps |
| Visual | `toMatchScreenshot()` built in ([docs](https://vitest.dev/guide/browser/visual-regression-testing)) | n/a |
| Breaking changes to note | v5: locators **strict by default**, `clearMocks: true`, unawaited `resolves/rejects` fail | – |

**Recommendation:** use **Browser Mode as the default for anything that renders**, with `vitest-browser-react` for `render` and `page.getByRole(...)` locators. Run Chromium on PRs and all three engines on `main` and nightly. Base UI has scripts for all three engines; whether its CI runs all three was not checked. Use a **node-environment project** (no DOM) for pure utilities, token transforms, and the SSR suite (§6.1). Do not add jsdom for component behaviour. The only reason to keep jsdom would be a Base UI-style "both environments" matrix, which this project does not need.

Playwright's own component testing is **not** an option: the experimental CT packages are frozen as of 1.63. Its new "stories/gallery" model (1.62) is worth watching but is new and has little adoption.

```ts
// vitest.config.ts (root): projects inherit root config by default in Vitest 5
import { defineConfig } from 'vitest/config';
import { playwright } from '@vitest/browser-playwright';
import { storybookTest } from '@storybook/addon-vitest/vitest-plugin';
import { argosVitestPlugin } from '@argos-ci/storybook/vitest-plugin';

const browsers = process.env.ALL_BROWSERS
  ? [{ browser: 'chromium' }, { browser: 'firefox' }, { browser: 'webkit' }]
  : [{ browser: 'chromium' }];

export default defineConfig({
  test: {
    projects: [
      {
        test: {
          name: 'unit',
          include: ['packages/*/src/**/*.test.{ts,tsx}'],
          browser: { enabled: true, headless: true, provider: playwright(), instances: browsers },
          setupFiles: ['./test/setup.browser.ts'], // fail-on-console, axe helper
        },
      },
      {
        plugins: [
          storybookTest({ configDir: '.storybook' }),
          argosVitestPlugin({ uploadToArgos: !!process.env.CI }),
        ],
        test: {
          name: 'storybook',
          browser: { enabled: true, headless: true, provider: playwright(), instances: [{ browser: 'chromium' }] },
          setupFiles: ['./.storybook/vitest.setup.ts'],
        },
      },
      {
        test: {
          name: 'ssr',
          environment: 'node', // no DOM on purpose: catches window/document access during render
          include: ['test/ssr/**/*.test.tsx'],
        },
      },
    ],
  },
});
```

Fail on any console warning or error. Unexpected React warnings, including hydration warnings, are bugs. MUI uses `vitest-fail-on-console` for this.

## 4. Accessibility QA

### 4.1 Automated layers

| Layer | Tool | Gate |
|---|---|---|
| Lint | **oxlint** `jsx_a11y/*` (37 rules) | PR blocks on error. `eslint-plugin-jsx-a11y` is rejected: last release Oct 2024, and its peer range stops at ESLint 9 |
| Story-level | `@storybook/addon-a11y` with `parameters.a11y.test: 'error'`, running through the Vitest addon | PR blocks. Per-story opt-outs need a code comment linking an issue |
| Behaviour | Vitest browser tests for keyboard maps, focus management and ARIA states, following the WAI-ARIA APG pattern per widget | PR blocks |
| Page-level | `@axe-core/playwright` on docs pages and fixture apps (light, dark, forced-colours, reduced-motion) | PR blocks on fixture pages; nightly on the full docs site |
| Screen reader | Guidepup NVDA (Windows) and VoiceOver (macOS) | Nightly and pre-release. Not PR-blocking at first because of flake risk |

**Two version traps found during research:**
1. **axe-core version skew.** The Storybook a11y addon depends on `axe-core ^4.2.0`, which resolves to **4.14.0**. 4.14 turned on `label-content-name-mismatch` by default. `@axe-core/playwright@4.13.0` pins `~4.13.0`. Without intervention, Storybook and Playwright will report **different rule sets**. Fix with one pinned version:
   ```jsonc
   // package.json (root)
   "pnpm": { "overrides": { "axe-core": "4.14.0" } }
   ```
2. **ESLint 10 vs jsx-a11y.** Explained in the Lint row above.

The `wcag22aa` tag exists in axe-core ([API.md tags table](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)). axe is commonly cited as catching **up to 57% of WCAG issues** automatically (figure from Storybook a11y addon material surfaced by search; **UNVERIFIED** on the current docs page: https://storybook.js.org/docs/writing-tests/accessibility-testing), so manual testing is required, not optional.

Also automate cheaply in Vitest browser mode:
- **forced-colors**: `page.emulateMedia({ forcedColors: 'active' })` through the Playwright provider's page (fixture apps), or a story mode.
- **prefers-reduced-motion**: the Motion variables' "Reduced" mode must produce no transform or opacity animation. Assert computed `transition-duration` / `animation-duration`.
- **Target size (WCAG 2.2 SC 2.5.8)**: axe's `target-size` rule, plus a Vitest check that interactive components at `size="sm"` have a box of at least 24×24 CSS px.
- **Focus appearance**: assert that the focus-ring token renders an outline of at least 2px, with contrast against `bg/surface` in both themes.

### 4.2 Manual screen-reader and assistive-tech test matrix

Run before every minor release, for each changed component, and on all components before 1.0. Store results in `docs/a11y/<component>.md`. The docs site renders them as a "Accessibility support" table per component.

| AT | Browser | OS | Priority | Cadence |
|---|---|---|---|---|
| NVDA (latest) | Chrome, Firefox | Windows 11 | P0 | Each minor; automated subset nightly (Guidepup) |

## 7. TypeScript 7 and props tables (the load-bearing finding)

**Facts:**
- `typescript@7.0.2` (2026-07-08) is the Go-native compiler. In the npm package, the `.` export exposes only version info (`version`, `versionMajorMinor`); the compiler API is gone and only `./unstable/*` remains (export map verified in the registry manifest; contents of `.` per the [fork issue](https://github.com/cyberuni/react-docgen-typescript/issues/1)). A stable programmatic API is expected in **7.1** (Q4 2026, **UNVERIFIED** date) ([announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), [Nx KB](https://nx.dev/docs/kb/typescript-7)).
- `react-docgen-typescript@2.4.0` **crashes on TS 7** with `TypeError: Cannot read properties of undefined (reading 'fileExists')` ([issue](https://github.com/cyberuni/react-docgen-typescript/issues/1)). Upstream's last commit was 2025-06-10. Storybook's `reactDocgen: 'react-docgen-typescript'` therefore fails under TS 7 ([nearform/quantum#1019](https://github.com/nearform/quantum/issues/1019)).
- `ts-morph@28` bundles **TS 6.0.2** internally (verified in the `@ts-morph/common` tarball), so it works regardless of the repo's `typescript` version. It parses with the 6.0 grammar, which matters only if public types use TS-7-only syntax (avoid that).
- `fumadocs-typescript@5.5.2` already runs on TS 7 through `typescript/unstable/sync`. It works today, but on an API surface Microsoft explicitly labels unstable.
- Base UI's pattern: `"typescript": "npm:@typescript/typescript6@6.0.2"` (for tooling that imports the JS API, such as typescript-eslint and docgen) and `"@typescript/native": "npm:typescript@7.0.2"` (for fast `tsc -b`).

**Docgen comparison:**

| Option | TS 7 safe | Accuracy | Speed | Coupling |
|---|---|---|---|---|
| `react-docgen` 8 (Babel) | Yes (no TS dependency) | Partial: imported/aliased types are resolved less well ([Storybook docs](https://storybook.js.org/docs/api/main-config/main-config-typescript)) | Fast | Storybook default |
| `react-docgen-typescript` 2.4 | **No** | High | Slow | Upstream inactive |
| **ts-morph 28 custom extractor** | **Yes (bundled TS 6.0.2)** | High: full type checker | Medium; cached | None. Emits JSON consumed by anything |
| `fumadocs-typescript` 5.5 AutoTypeTable | Yes (unstable API) | High | Medium; FS cache | Fumadocs |
| `@microsoft/api-extractor` 7.59 | **UNVERIFIED** with TS 7 | API-report level, not props | – | Useful for API diff, not tables |

**Recommendation:**
1. Build and typecheck with TS 7 (`@typescript/native`). Alias `typescript` to `@typescript/typescript6` for JS-API tooling until 7.1.
2. Storybook: `reactDocgen: 'react-docgen'`. Controls only need rough types; the docs site is the source of truth.
3. **Component API manifest**: `scripts/extract-api.ts` (ts-morph) walks each `packages/react/src/*/index.ts`, reads exported `*Props` interfaces and TSDoc (`@default`, `@deprecated`, `@since`, `@internal`, `@experimental`), and writes `api/<Component>.json` with props, data-attributes (`data-state`, `data-disabled`, …), CSS custom properties (`--nz-*`) and slots. The manifest feeds:
   - docs props tables (Fumadocs `<TypeTable type={…}/>`, which accepts a plain object);
   - an **API-diff check** in CI (any removed or renamed prop without a major changeset fails);
   - size-limit entry generation (§9);
   - optional Storybook `argTypes` enrichment, and `llms.txt` / MCP for AI tooling.
4. Revisit when TS 7.1 ships: either move the extractor to the stable TS 7 API or switch to `fumadocs-typescript`. Either change touches one script.

```ts
// scripts/extract-api.ts (sketch)
import { Project, Node } from 'ts-morph';
import { writeFileSync, mkdirSync } from 'node:fs';

const project = new Project({ tsConfigFilePath: 'packages/react/tsconfig.json' });
for (const entry of project.getSourceFiles('packages/react/src/*/index.ts')) {
  for (const [name, decls] of entry.getExportedDeclarations()) {
    if (!name.endsWith('Props')) continue;
    const decl = decls[0];
    const type = decl.getType();
    const props = type.getProperties().map((sym) => {
      const d = sym.getDeclarations()[0];
      const docs = Node.isJSDocable(d) ? d.getJsDocs().at(-1) : undefined;
      const tag = (t: string) => docs?.getTags().find((x) => x.getTagName() === t)?.getCommentText();
      if (docs?.getTags().some((x) => x.getTagName() === 'internal')) return null;
      return {
        name: sym.getName(),
        type: sym.getTypeAtLocation(decl).getText(decl),
        required: !sym.isOptional(),
        default: tag('default') ?? null,
        deprecated: tag('deprecated') ?? null,
        description: docs?.getDescription().trim() ?? '',
      };
    }).filter(Boolean);
    mkdirSync('api', { recursive: true });
    writeFileSync(`api/${name.replace(/Props$/, '')}.json`, JSON.stringify({ name, props }, null, 2));
  }
}
```

### 11.3 Semver, deprecation and LTS policy

**Public API** (covered by semver): package entry points and `exports` paths; component names and props; documented **data-attributes** (`data-state`, `data-slot`, …); **CSS custom property names** (`--nz-*`) and token names; CSS cascade-layer names; documented class names; keyboard interactions and ARIA semantics. Accessibility regressions are treated as bugs and fixed in patches; intentional a11y behaviour changes count as breaking.

**Not public:** DOM structure beyond documented slots, internal class names, `@internal` exports, anything under `@nizivo/*/experimental`. Visual refinements (token value changes) ship in **minor** releases with a changelog entry and an Argos-reviewed diff.

**Stability tiers** per component, recorded in the manifest and shown as docs badges:
- `experimental`: imported from `@nizivo/react/experimental/*`; can break in a minor. Use this tier for the 3D/shader/motion lab and Instagram storefront components.
- `beta`: semver applies, with breaking changes allowed in minors after one deprecation cycle.
- `stable`: full semver.
- `deprecated`.

**Pre-1.0:** `0.x`, where a minor bump means breaking. Publish 1.0 once core actions/forms/overlays reach `stable`.

**Deprecation:** mark with TSDoc `@deprecated` (surfaces in IDEs and in the manifest). Emit a **dev-only** `console.warn` once per symbol, guarded by `process.env.NODE_ENV !== 'production'` so production bundles strip it. Give a docs migration note and a codemod (`npx @nizivo/codemod <transform>`) when the change is mechanical. Remove deprecated APIs **no earlier than the next major and at least 6 months after deprecation**. The CI API-diff check (manifest) fails if a prop is removed without a `major` changeset.

**LTS:** the current major gets everything. The previous major gets **security and critical a11y fixes for 12 months** after the next major ships. Earlier majors are unsupported. Publish this as a table in `SECURITY.md` and on the docs. State a **React support window** (for example, the current React major plus the previous minor line) and a **browser support** policy (for example, Baseline Widely Available), both decided in the architecture track.

### 11.4 Release pipeline (npm changes are the time-critical part)

Facts:
- Since **2026-07-31**, 2FA-bypass granular tokens can no longer manage tokens, maintainers, trusted-publishing config or org membership. **January 2027** is the target date for removing their direct-publish capability ([GitHub changelog](https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/)).
- **Trusted publishing (OIDC)** requirements ([docs](https://docs.npmjs.com/trusted-publishers)):
  - npm CLI ≥11.5.1 and Node ≥22.14;
  - an exact workflow **filename** (case-sensitive) and an optional environment;
  - **reusable workflows and `workflow_dispatch` can mismatch**;
  - at most 10 trusted publishers per package;
  - a new config **expires if there is no successful publish within 2 days**;
  - `repository.url` must match exactly;
  - provenance is automatic for public repo + public package;
  - GitHub-hosted runners only.
- **Staged publishing** has been GA since 2026-05-22 (npm ≥11.15.0): `npm stage publish`, then a maintainer approves with 2FA. A trusted publisher can be restricted to **stage-only** ([changelog](https://github.blog/changelog/2026-05-22-staged-publishing-and-new-install-time-controls-for-npm/)). Since **2026-10-02**, `npm stage publish` can **create new packages**, including public scoped ones, so no manual first publish is needed. Trusted publishing is configured afterwards ([changelog](https://github.blog/changelog/2026-10-02-npm-staged-publishing-now-supports-creating-new-packages)).
- **Changesets 3** (3.0.0 on 2026-08-11, 3.0.3 on 2026-09-14) pairs with **`changesets/action@v2`**. Field reports say v2 renamed its inputs (`version-script`, `publish-script`, `github-token`) and that CLI 3 publishes through the package manager; **UNVERIFIED** against the official README. One npm/cli issue reports E404 when publishing scoped packages over OIDC from changesets/action ([npm/cli#8976](https://github.com/npm/cli/issues/8976)); its current status is **UNVERIFIED**.

Plan:
1. Create the `@nizivo` npm org. Owners are 2–3 humans with hardware-key 2FA. Do not create automation tokens.
2. Bootstrap each new package with `npm stage publish` (CI or local) and approve it with 2FA. Then add a trusted publisher per package: GitHub org `neev-technologies` (exact case), repo, `release.yml`, environment `npm-publish`.
3. Use **stage-only** while in 0.x and for every **major**. Allow direct `npm publish` from OIDC for patch and minor releases once the pipeline is proven. This is a policy choice.
4. Protect the GitHub environment `npm-publish` with required reviewers and restrict it to the `main` branch.
5. Before shipping 1.0, run a throwaway-package rehearsal of the full OIDC + Changesets path.

```yaml
# .github/workflows/release.yml   (filename must match the npm trusted-publisher config)
name: release
on:
  push:
    branches: [main]
concurrency: { group: release, cancel-in-progress: false }
permissions:
  contents: write        # version PR, tags, GitHub releases
  pull-requests: write
  id-token: write        # npm OIDC trusted publishing + provenance
jobs:
  release:
    runs-on: ubuntu-latest
    environment: npm-publish
    steps:
      - uses: actions/checkout@v5            # pin to SHA in practice
      - uses: pnpm/action-setup@v4           # pin to SHA
      - uses: actions/setup-node@v5          # pin to SHA
        with: { node-version: 24, registry-url: 'https://registry.npmjs.org' }
      - run: npm install -g npm@12           # >=11.5.1 for OIDC, >=11.15.0 for `npm stage`
      - run: pnpm install --frozen-lockfile
      - run: pnpm build && pnpm -r pack --pack-destination .tarballs && pnpm check:package   # publint + attw + node-resolution
      - uses: changesets/action@v2           # input names UNVERIFIED, check README before use
        with:
          version-script: pnpm changeset version
          publish-script: pnpm release       # e.g. `changeset publish`, or a script that runs `npm stage publish` per package
          github-token: ${{ secrets.GITHUB_TOKEN }}
```

## 12. Publishing a Figma Community file alongside the library

**Facts (Figma Help Center):**
- Publishing Design files is available on **any plan**. Anyone with *can edit* access can publish to their personal profile. **Only team owners and admins can publish to a team profile**, and the file must live in that team. A published file cannot later move to another team ([permissions](https://help.figma.com/hc/en-us/articles/360041423614-Community-publishing-permissions), [publish](https://help.figma.com/hc/en-us/articles/360040035974-Publish-files-to-the-Figma-Community)).
- Free Community files are licensed **CC BY 4.0**. Creators may add further licences but cannot remove CC BY ([licensing](https://help.figma.com/hc/en-us/articles/360042296374-Figma-Community-copyright-and-licensing)).
- An update publishes a **new version**. **Existing duplicates are not updated**, so users must duplicate again. Likes and duplicate counts carry over. For team-profile files, only that team's admins can publish updates.
- Listing metadata: name, description, category, up to 5 tags, a thumbnail plus up to 9 images at 1920×1080, and a support email or website.
- Users consume a Community file by **duplicating it and publishing it as their own library**. I found no official way to subscribe to a Community file as a live library (**UNVERIFIED** that none exists).
- **Plan gates that affect the design-to-code story:** **Code Connect** needs an Organization or Enterprise plan (v2.0 shipped Aug 2026, plan requirement unchanged) ([help](https://help.figma.com/hc/en-us/articles/23920389749655-Code-Connect)). The **Variables REST API** is Enterprise-only ([docs](https://developers.figma.com/docs/rest-api/variables-endpoints)). On Starter/Pro, token export must go through a **plugin** (custom plugin or MCP/plugin-API script), not REST, and Code Connect becomes available only after an Organization-plan upgrade.

**Plan:**
1. **Create a clean distributable copy.** Do not publish the working file. From the token snapshot:
   - delete the foreign variable collections (Clario, Pipkin, Pipkin Soft, Merit, Ashgrove, Noema, Praxa, Pogo, Halden, Ardenfield) and their roughly 130 text styles;
   - unsubscribe from the unused Community libraries (Material 3, Simple Design System, Apple OS kits);
   - rename `grove` to `nizivo` in variable names and `codeSyntax` (`var(--nz-…)`).
2. Put the file in a **"Nizivo UI (Community)" team** owned by Neev and publish to that **team profile**.
3. Add a **Cover** (1920×1080), a **Getting started** page (npm install, docs URL, GitHub, licence note covering CC BY 4.0 for the file and Apache-2.0 for the code, and Geist/OFL font note), a **Changelog** page, and **"vX.Y.Z" in the file name and cover**, because duplicates do not auto-update.
4. In each main component, fill in the **description** and the **documentation link** to the docs page (`https://nizivo.dev/components/button`). This is the Starter/Pro substitute for Code Connect. Keep component property names identical to React prop names so the manifest and Figma line up.
5. **Release cadence:** publish a Community update with every **minor** library release, as a step in the release checklist. Patch releases do not need a Figma update unless tokens changed.
6. **Token sync stays one-directional and plugin-driven:** Figma → `tokens.json` through a plugin export or MCP script → reviewed PR → Style Dictionary or similar (tokens track). A CI check compares exported token names against the manifest's `--nz-*` usage.
7. Support contact: the GitHub Discussions URL. The listing must not imply an official affiliation with anyone else; the brand is Neev's own.

## 14. Risks

1. **TS 7.1 API timing.** If 7.1 slips, the `@typescript/typescript6` alias stays longer. Fumadocs' unstable-API usage could break on TS patch releases, which is why the ts-morph manifest is the primary path.
2. **VRT cost creep.** The responsive and theme matrix multiplies counts. Keep the selective-mode policy and run full matrices on merge-queue only. Revisit Chromatic OSS once there are more than 5 contributors.
3. **Argos plan terms.** Hobby is "for personal projects" and sponsorship requires "not for commercial use". Budget Pro ($100/mo) and do not count on free.
4. **Screen-reader automation flakiness** on hosted Windows and macOS runners. Keep it non-blocking until it is stable for 30 days.
5. **npm OIDC + Changesets 3 edge cases** (scoped-package E404 report, renamed action inputs, the 2-day expiry of an unused trusted-publisher config). Rehearse with a throwaway package and keep stage-only publishing as the safety net.
6. **Storybook 11 migration** (Node 22.12+, Vite 7+, TS 5.9+). Small, because stories are CSF3 and the framework is `react-vite`.
7. **axe-core drift** between tools, solved by a pnpm override. Re-evaluate on every axe minor, because new default-on rules (such as 4.14's) can break CI.
8. **Fixture maintenance.** Six framework apps on fast-moving majors (React Router already moved to v8). Renovate groups per fixture; one fixture failing should not block unrelated packages (path-filtered matrix).
9. **Figma file drift.** Duplicates never update, so users stay on stale versions. Mitigate with the version stamp and changelog page.
10. **Licence choice** needs Neev legal review. Apache-2.0 is GPLv2-incompatible, which rarely matters for UI libraries.
