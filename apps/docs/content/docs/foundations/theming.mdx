## How themes work

Every semantic colour is one `light-dark()` value, declared once on `:root`. Which side applies depends
on the element's `color-scheme`, which `data-nz-theme` sets:

| Attribute                | Effect                                                 |
| ------------------------ | ------------------------------------------------------ |
| none                     | Light. Nizivo never follows the OS unless you opt in.  |
| `data-nz-theme="system"` | Follows the operating system (`prefers-color-scheme`). |
| `data-nz-theme="light"`  | Light, whatever the OS says.                           |
| `data-nz-theme="dark"`   | Dark. Dark is a preview until design reviews it.       |

## Inverse surfaces

A Tooltip or a `tone="inverse"` Card renders `data-nz-scheme="inverse"`, which sets
`color-scheme` to the opposite of the surrounding theme. Every token inside resolves in that scheme, so
there is no separate "on-inverse" token family. An inverse surface inside another inverse surface stays
inverse; it does not flip back.

## This site's theme switch

The theme switch (at the foot of the sidebar on these pages, in the top bar on the home page) is
Fumadocs' own, built on `next-themes`. It offers Light, Dark and System, and it writes two things on
`<html>`:

- the `dark` class, which Fumadocs' styles key on;
- `data-nz-theme="light"` or `"dark"`, which Nizivo's tokens key on.

"System" resolves to light or dark from `prefers-color-scheme`. A small inline script in `<head>`
applies the stored choice to both before `<body>` exists, so the first paint is already in the right
theme; `next-themes` then keeps them in step. Its own script runs inside `<body>`, which is too late to
rule out a flash. Fumadocs' colour variables are mapped onto Nizivo's
tokens (`--color-fd-background: var(--nz-bg-canvas)` and so on), so the docs chrome and every live
example change together, with no flash on load.

Nizivo's own `ThemeScript`, a small server-safe script that persists the user's choice the same way, is
planned and is not in the package yet.

## Rebrand with tokens

Write your theme in `light-dark()`, inside the `nz.themes` layer, and start the file with the layer
order statement that opens every Nizivo stylesheet. Layer order is fixed by the first stylesheet that
names a layer, so with that line your theme beats the base tokens whatever order the files load in;
without it, a theme that loads before `tokens.css` puts `nz.themes` first, and the base tokens win:

```css
/* The order every Nizivo stylesheet declares; repeat it before any nz.* rule of your own. */
@layer nz.tokens, nz.themes, nz.reset, nz.base, nz.components, nz.patterns, nz.utilities;

/* Rebrand globally; both themes in one declaration. */
@layer nz.themes {
  :root {
    --nz-bg-brand: light-dark(#5b21b6, #a78bfa);
    --nz-text-on-brand: light-dark(#fff, #1e1b4b);
  }
}

/* Rebrand one subtree. */
.marketing {
  --nz-radius-md: 999px;
}

/* Restyle one component everywhere through its public hook. */
.nz-card {
  --nz-card-padding: var(--nz-space-5);
}
```

Unlayered CSS beats every layer, so a theme written outside any layer needs no order line. With the
[Tailwind recipe](/docs/getting-started/tailwind/), Nizivo's layers sit inside Tailwind's `components`
layer, so write the theme there unlayered.

Keep `light-dark()` inside custom properties, as above. Written directly on `background`, `border` or
`box-shadow` with literal colours, it takes the wrong scheme in nested scopes on Firefox 129–131 (see
[Deviations from Figma](/docs/deviations/#browser-degradations)).

## Reduced motion

`prefers-reduced-motion: reduce` or `data-nz-motion="reduce"` on any element swaps the motion tokens to
their reduced values. See [Motion](/docs/foundations/motion/).
