## What week 6 built

- **Select in a Field** (§10.3, §16.1): `SelectRoot` calls `useFieldControl({ name, required, disabled, invalid, labelBehavior: 'focus' })`; Select's own props win, an explicit `false` included. The trigger takes the Field control id, `aria-labelledby` (value id, then the Field label id) and `aria-describedby` (description, error, then its own). The Field's `name` and `required` reach React Aria's hidden native `<select>`, so the value is in `FormData`. A label click focuses the trigger with its ring and never opens the list: `labelBehavior: 'focus'` is a new `useFieldControl` option, handled inside FieldScope, which renders the label (a registered `onClick` that calls `preventDefault` and `label.control.focus({ focusVisible: true })`). The server HTML and the zero-JS path are unchanged. New example: `SelectFieldExample`.
- **The `select.css` pass** (figma/13 §4.3): the trigger matches NativeSelect in every state (sm radius, invalid border and critical halo, disabled and disabled-fieldset `--nz-border-subtle`, the focus halo, transitions, value ellipsis). The popup and rows copy Menu's recipe: `--nz-radius-lg`, a 1 px `--nz-border-subtle` border, `--nz-elevation-3`, 36 px rows 2 px apart, Body/M, the inset ring, the selected row `--nz-bg-brand-subtle` with `--nz-text-brand` and a trailing check (`span.nz-select-item-indicator`; the new `SelectItem` `indicator` prop replaces it, `null` removes it), Menu's group label and separator. In forced colours a selected row stays `Highlight`, hovered or not. `select.css` is 4,379 B raw.
- **`Dialog.Close` default** (§12.3, §14.2): with no `render` and no `children` it is a tertiary `md` IconButton showing core's `close` glyph, named "Close" (`labels.close` or `aria-label` override it). A direct child of `Dialog.Popup` sits in the top-end corner, 20 px from both edges, positioned against the popup (which never clips), so its ring always shows. A control placed directly in the content and flush with its edge now draws its ring inside itself, so the content's `overflow: clip` (Figma's corner clip) no longer cuts it. An alertdialog focuses the `Dialog.Close` in its footer (Cancel) before the corner X. The markup is IconButton's, written out (importing `iconButtonElement` cost about 280 B gzip against the Dialog cap); a browser case asserts it equals `<IconButton tooltip={false}>`'s output. `dialog/component.json` `cssDeps` gains `icon-button`.
- **O-11 focus return** (§12.2): `Dialog.Root` takes `returnFocus` (default `true`, or an element ref, a function returning an element, or `false`). The family's `ReturnFocus` (`_engines/react-aria/popup.client.tsx`, used by Dialog, Menu and Select) runs the whole chain: `returnFocus` (it overrides React Aria's own restore through React Aria's cancelable `react-aria-focus-scope-restore` event), then the trigger, then the element that opened the popup, then the parent overlay's trigger (a registry of the family's open popups), then `<body>` with a development warning that production builds drop (0 occurrences of the text in the dialog, menu and select bundles with `NODE_ENV=production`). Menu and Select run the chain but take no prop yet.
- **Tooltip stuck in `data-exiting`** (React Aria 1.22.1, react-stately 3.51.0): when another tooltip opens during warm-up, the first is closed "instantly" (`hideTooltip(true, true)`); React Aria's Tooltip returns `null` mid-exit, `useAnimation` never calls `onEnd`, and the exit state stays `exiting`. The next ordinary close (a press with no pointer move after keyboard use) then mounts an unpositioned popup in `data-exiting` that never leaves. The adapter keys React Aria's Tooltip on that instant-close state (`_engines/react-aria/tooltip.client.tsx`), which resets it. A regression case fails without the fix and passes with it in Chromium and WebKit.
- **`ThemeScript`, the theme half** (§7.4, D-al): before first paint it reads `localStorage` key `nz-theme`; an exact `light`, `dark` or `system` replaces the server's `data-nz-theme` on `<html>`. Nothing stored, any other value, or blocked storage leaves the server value. `system` is written literally and CSS follows the OS. The theme part and the platform part each sit in their own `try`, so the script never throws and blocked storage never stops `data-nz-platform`. The only prop is still `nonce`. The script is 379 bytes (257 before), and its hash is `sha256-nA1HUQWDdDUFqqoxWbjzCzcYSjzWLEe0pwDdRCMGqOw=`, pinned by `test/ssr/theme-script.test.tsx` and quoted in its JSDoc, the README and the Next guide. The docs site replaced its own `<head>` script with `<ThemeScript />` (its switch stores under `nz-theme`, and code highlighting follows `data-nz-theme` through `light-dark()`). The three fixtures dropped their own stored-choice scripts, so their `stored` theme-flash case now tests `ThemeScript`.
- **`@nizivo/react/styles.css`** (§5.2): the canonical `@layer` statement, a byte-identical copy of `@nizivo/tokens`' `tokens.css`, `base.css`, then the 36 stable component sheets sorted by name (`reset.css` and unstable components are not in it), each sheet as built, so the file is an exact concatenation (a dist test checks it). The export `./styles.css` is in `package.json`, and a missing or wrong export now fails the CSS build. `check:release` needed no change: the tarball allowlist takes `.css` under `dist/` (react: 254 files), and attw skips CSS entries. The docs catalog and example generator now skip every file export, not only `./css/*`.
- **Docs:** every Dialog and Tooltip example composes a Button into the trigger (the two server-open examples too, so the SSR test's regexes follow), and the Dialog and Tooltip pages say why (WCAG 2.2 2.5.8 target size). Whether a bare trigger should get a minimum size of its own is not decided (reported). ## Week 6 review

Three reviewers (overlays and accessibility; CSS, visual and floor; theme, release and plan) filed 21 findings against the integrated tree. 8 were fixed before the week 6 commits and F1 in part, 1 was rejected, and 11 are deferred to their owners with a reason, with the rest of F1; none of the deferred ones is a change the plan lets a builder decide. Fixed:

- **A form reset left a Select's hidden `<select>` empty (R1-1).** React Aria 1.22.1 resets the Select's state on the form's `reset`, then the browser resets the hidden native `<select>` to its empty first option, and React never writes the value back: the trigger showed the default while `FormData` had `''`, and a required Select blocked the next submit with nothing visibly wrong. Same with or without a Field and with a bare React Aria Select, so it predates week 6.
